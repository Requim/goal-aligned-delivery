# 原理映射：把理论变成决定

这是一套工程控制方法，不是“保证模型 100% 正确”的宣称。模型可能依据不完整上下文给出看似合理的动作；工程控制针对其外部行为与结果，不改变模型权重。

| 阶段 | AI 层面的风险 | 工程原理为什么有效 | 要落实的机制 |
| --- | --- | --- | --- |
| 目标契约 | 自然语言没有表达的约束由模型补充 | 抽象把目标变成稳定业务对象；契约明确输入、输出、前置/后置条件；追踪关系减少分解时丢失目标 | AC 编号、禁止行为、完成与部分完成边界 |
| 状态核对 | 上下文是曾被提供的信息，不等于当前事实 | 配置与材料管理把事实绑定权威来源；适当的版本记录让验收针对确定对象 | 资料/数据修订；相关时才加源码、配置与运行检查 |
| 行动边界 | 理解正确仍可能选错工具或参数 | 信任边界规定谁能决定事实；最小权限减少可出错动作和影响范围；关注点分离让确定性计算不被生成文本改写 | 服务端校验、受限数据接口、结果绑定 |
| 独立判据 | 实现和测试可能共享同一错误假设 | 不变量不依赖当前实现；独立预期能区分正确和错误；反例/蜕变关系提高反馈的区分力 | 手算期望、范围隔离、坏版本测试失败 |
| 用户链路 | 局部子目标完成不推出整体目标完成 | 分解管理复杂度，整体核对检验组合后是否仍满足目标 | 内容任务核对成稿，软件任务分层测试，数据任务从输入重算 |
| 证据诊断 | 相同表象可以对应多个原因，模型可能猜测 | 可观测性提供可区分假设的观察；小步变更减少同时变化的变量 | 原文定位、差异、计算过程；软件再用 requestId 和阶段日志 |
| 验收回归 | 自评与生成过程可能共享盲点；后续动作可能重犯 | 独立验收定义判据；反馈闭环把实际与目标比较后修正；回归保存已知错误的检查能力 | 业务验收、红到绿复现、受影响用例重跑 |
| 变更恢复 | 多个会话观察不同状态，局部正确可能组合错误 | 并发控制和基线核对避免丢失更新；发布门禁限制传播；可恢复性降低失败代价 | 发布前重验、兼容迁移、受控切换与回滚 |

## 不混淆的概念

- 独立判据不等于换一个模型：预期来自业务规则、可信基准或手算例子，且不是调用被测实现来生成预期。
- 反馈控制是“目标 → 执行 → 观察 → 比较 → 修正 → 复验”，不是只有模型收到一句“失败了”。没有有效判据，闭环会向错误目标反复优化。
- 契约减少语义歧义，不证明用户目标一定被完整表达；重大歧义仍须核对。
- 权威服务可以有缺陷。权限限制调用方，业务测试验证服务本身，二者不能互相替代。
- 校验结构不等于校验语义；ID 相等不等于实际几何、统计口径和单位一致。
- “测试通过”只约束测试过的场景和版本。持续回归降低复发风险，不覆盖所有未来错误。
- 接口 200、JSON 合法、浏览器有数字、Agent 自述均不是完整业务验收。
- Skill 是加载给 Agent 的工作指令和资源，不是绕不过去的安全边界。访问控制由运行系统执行；发布硬门禁由受保护的 CI/部署入口执行。
