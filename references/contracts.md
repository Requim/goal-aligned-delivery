# 任务契约与验收证据

## 先用最小契约

小任务可直接在对话中写明目标、禁止行为、关键验收项和验证方式。跨步骤或长任务复用已有记录，不维护相互矛盾的多份“当前状态”。

```text
目标与受众：用户需要什么结果、用于什么场景
交付物：回答/文档/表格/方案/代码/外部操作等，具体格式是什么
范围与非目标：本轮包含什么、明确不做什么
前置条件：需要的资料、数据、能力、环境和授权，哪些已经具备
关键约束：事实来源/对象/时段/单位/语气/风格/权限中实际相关的项
AC-1：输入和操作 → 预期结果 → 反例 → 检查/观察方法
AC-2：...
完成边界：核心产物与可接受的部分交付，缺少证据时如何说明
产物追踪：AC → 内容/实现位置 → 检查方法 → 本次证据
变更边界：哪些变化使证据失效、哪些操作需要另行授权
```

## 可选机器检查

只有需要持久验收记录或接入现有流水线时使用下面的 JSON。小任务无需填 JSON，普通内容交付也不要求建立 CI。已有可信校验设施时优先复用。

`contract.json` 由业务规格确定；在实施前固定，变更须记录原因，不能为了过关删掉验收项。

```json
{
  "schema_version": 1,
  "task_id": "deliverable-001",
  "goal": "按用户指定材料、范围与形式交付目标产物",
  "state": {
    "input_revision": "本轮实际输入材料或数据的版本",
    "criteria_revision": "本轮验收规则的版本"
  },
  "criteria": [
    {"id": "AC-1", "description": "替换为本轮核心结果及其具体可检查条件", "environment": "local-review"},
    {"id": "AC-2", "description": "替换为本轮关键约束及能区分错误的判据", "environment": "local-review"}
  ]
}
```

所有 criteria 均为本轮必需，不提供 `required: false` 绕过开关。只列实际相关条件，不把本模板的抽象句子作为真正的验收标准。开发部署任务若需生产验收，另列 `environment: production`，不能拿 isolated 代替。环境标签是声明，脚本无法远程证明它。

`evidence.json` 在真正执行验证后生成：

```json
{
  "schema_version": 1,
  "task_id": "deliverable-001",
  "contract_sha256": "contract.json 原始字节的 SHA-256",
  "observed_state": {
    "input_revision": "与契约绑定的当前输入版本一致",
    "criteria_revision": "与契约绑定的规则版本一致"
  },
  "checks": [
    {
      "criterion_id": "AC-1",
      "status": "passed",
      "environment": "local-review",
      "observation": "实际检查方式、时间、预期与观察结果；不把计划当已执行",
      "artifacts": [
        {"path": "evidence/check-result.txt", "sha256": "该证据文件原始字节的 SHA-256"}
      ]
    }
  ]
}
```

这是格式演示，不是通过的证据；AC-2 缺失时脚本必失败。替换所有示意值，不能原样当真实记录。

运行：

```text
python -X utf8 <skill-dir>/scripts/check_delivery.py contract.json evidence.json --root <evidence-dir>
```

- 退出 `0`：必需项均声明通过，覆盖与版本相符，证据文件存在且摘要匹配。
- 退出 `1`：验收证据缺失、失败、阻塞、未验证，或版本/摘要不一致。
- 退出 `2`：输入格式、路径、重复字段/标识或文件读取错误。
- `status` 允许 `passed / failed / blocked / unverified`；后三种均不能通过完整验收。
- 路径必须在 `--root` 内，为普通文件；绝对路径、向外穿越和通过链接指向外部均拒绝。
- 脚本只读文件，不执行记录中的命令，不部署、不下载、不改变环境。

## 时效与当前状态

原有 `schema_version: 1` 继续兼容。需要时间校验时，仅将 evidence 版本改为 `2`，并在每个 check 中增加实际验证时间：

```json
{"verified_at": "2026-09-17T08:30:00Z"}
```

这个片段需合入既有 check，不是完整证据。时间必须含时区，不能复制示例日期当成当前执行记录。contract 仍使用版本 1。

按本任务要求选择参数，而非对所有任务强加时限：

```text
python -X utf8 <skill-dir>/scripts/check_delivery.py contract.json evidence.json --root <evidence-dir> --current-state current-state.json --not-before <last-relevant-change-ISO8601> --max-age-seconds 900
```

- `--current-state`：由可信执行流程重新采集的当前版本映射，格式与 contract.state 相同；与基线不一致则拒绝。不能直接复制旧 evidence 伪装重新采样。
- `--not-before`：验证不能早于最后相关变更或本轮约定的验收起点，含时区。
- `--max-age-seconds`：可选的正整数时限；不是任何业务数据的有效期定义。边界时刻允许，超出才拒绝。
- 版本 2 的未来时间一律拒绝；无时区/非法时间为输入错误。
- 指定时间要求却提供无时间戳的 v1 证据时，返回未通过，不能以兼容性绕过时效。

墙钟新鲜不等于语义仍适用：刚运行的测试也可能测错对象。时间、当前对象、契约覆盖和真正业务判据需要共同检查。

## 可信度与 CI 边界

脚本能拒绝漏项、状态和时间不一致，不能验证日志真假、范围几何或文字可读性；有人同时修改文件、时间戳、版本映射和摘要依然可能通过。这不是签名系统，也不是恶意 Agent 的沙箱。时效参数不替代可信采样或实际验证。

真正 CI 门禁应在受保护任务中读取已批准的契约和待发布制品，运行实际业务测试并采集当前版本、日志与摘要，再执行检查；将非零退出接入阻止发布的步骤，限制提交者修改门禁和预期的权限。只有文档或本地脚本而未接入 CI 时，必须报告“未建立不可绕过的发布门禁”。

审批记录与密钥不放进证据。令牌、Cookie、个人数据、完整供应商响应不可落盘到普通日志。哈希提供一致性标识，不提供来源认证。

## 提交结果

按用户目标给出完成/部分完成/阻塞及核对依据。证据与本轮输入和产物版本绑定；涉及软件或外部依赖时，再明确本地、隔离、真实供应商和生产验证的区别。输入变化后旧证据是否适用按影响范围判断，不自动复用。

## 按任务具体化，而不是套领域案例

- 文档：可要求面向指定受众、保留原文关键限定、不得编造经历、输出指定篇幅；通过原文对照和可读性评审验收。
- 研究：可要求只使用已取得的来源、标注日期、区分证据与推断、说明信息缺口；通过来源检查和论证复核验收。
- 数据：可要求只统计指定对象与时段、单位统一、排除重复；通过独立重算和改变无关数据的反例验收。
- 开发：可要求特定用户操作成功、权限和范围不越界、旧行为保留；通过相关测试与真实链路验收。
- 创作或设计：使用用户参考、受众与风格约束评审，区分可量化条件与主观标准；不把字数或截图存在当整体质量。

示例中的指标不是所有任务的必填项。回归可以是程序测试，也可以是稳定的事实核对或评审清单。
