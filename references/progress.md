# 进度记录与续做

适用于标准/严格任务。进度记录保存“做到哪里、依据是什么、接下来做什么”，与最终交付物分别维护；只讨论的多步骤任务也可记录，但下一步不能擅自变成实施。

## 位置与创建

1. 用户指定了记录位置时沿用；否则优先复用当前任务已有的计划/状态文件，补足缺失字段，不再维护另一份当前状态。
2. 没有已有记录时，在当前工作区创建 `work/task-progress/<task-id>.md`。检查同名文件是否属于当前任务，不能覆盖别的任务。开始实际执行前写入目标、验收项、单元和下一步，之后逐项更新。
3. 首次汇报和本轮收尾给出实际路径；普通进度消息只说明关键变化，不反复贴全文。相对路径以任务工作区为基准；指向工作区外部时使用明确路径。
4. 用户禁止落盘或工作区不可写时不强行创建；用回复中的同等摘要交接，明确当前没有持久记录。缺少文件工具不等于已经保存。

不把各次任务记录存入 skill 目录或全局偏好文件；只记录必要的材料位置、版本和脱敏观察。

## 最小记录模板

字段按任务实际情况填写，未执行的检查明确写“未验证”。已有计划可将这些字段融入现有结构。

```markdown
# <任务名>

- 任务标识：<稳定 task-id>
- 最近更新：<实际当地时间，含时区>
- 目标与交付物：<结果、受众、实际输出位置>
- 范围与关键约束：<本轮包含项、禁止项、完成边界>
- 当前整体状态：进行中
- 当前阶段与下一步：<具体动作及对应单元>
- 输入基线：<原始材料位置/版本、已确认事实与缺口>

## 验收项

- AC-1：<预期结果与检查方法>
- AC-2：<预期结果与检查方法>

## 交付单元

| 单元 / 对应 AC | 当前状态 | 产物位置 | 检查与实际证据 | 下一步 / 依赖 |
| --- | --- | --- | --- | --- |
| U-1 / AC-1 | 进行中 | 尚未产出 | 未验证 | <下一具体动作> |
| U-2 / AC-2 | 待开始 | 尚未产出 | 未验证 | <前置条件> |

## 阻塞与未决事项

- <缺失什么、影响哪些单元、解除条件；无阻塞则写无>

## 关键决策与变更

- <实际时间：决策/需求变化、原因、受影响单元与需重验项目>
```

## 更新与状态

在以下事件发生后写回同一记录，再开始依赖该结果的后续动作：

| 事件 | 写入的变化 |
| --- | --- |
| 单元产出或检查结束 | 产物位置、实际观察、检查状态和单元状态 |
| 缺输入、执行失败或外部依赖不可用 | 影响范围、失败观察、解除条件与可继续的工作 |
| 用户调整目标、范围或输入 | 更新当前契约，保留变更原因；将受影响的完成项改为待验证或待处理 |
| 交接、明确暂停或本轮结束 | 当前整体状态、尚未完成项、下一步和最近更新时间 |

- 单元状态使用 `待开始 / 进行中 / 待验证 / 已完成 / 阻塞 / 已取消`。检查结果另写 `通过 / 失败 / 阻塞 / 未验证`，不把“已执行”当“通过”。
- 整体状态使用 `进行中 / 待验收 / 阻塞 / 已暂停 / 已完成 / 已取消`。部分单元阻塞而仍有可执行项时，整体保持进行中；所有剩余工作都依赖缺失条件时记阻塞。已暂停/已取消须有用户指示依据。
- 所需产物均具备但仍有必需检查时记待验收；所有必需单元验收通过且约定的完成边界满足，才记已完成。本轮回复结束不代表任务完成。
- 证据写实际检查方式、观察和可定位的产物/日志，不以计划中的命令作证据。无需强制 JSON、哈希或每条工具调用的流水账。
- 更新当前状态并保留关键决策；不将聊天全文复制为不断增长的日志。聊天中发过“已完成某步”后，仍须同步文件。

## 恢复与交接

1. 先确认记录属于当前任务，读取目标、当前状态、未完成单元、阻塞和下一步；缺字段时核对材料补齐，不重新执行已验证且未变化的工作。
2. 将最新用户输入与记录对照，检查相关输入版本、产物是否存在、证据是否仍对应当前内容。记录是恢复索引，不是真相来源；冲突时以用户最新要求及现场材料为准，记录差异。
3. 对变化影响到的单元撤回旧完成状态，写明待处理/待验证原因；保留未受影响的证据。用户补齐缺失材料后更新基线、解除相应阻塞并继续。
4. 从下一未完成项开始；执行并验证后写回同一文件。需要换对话或执行者时，交接原记录路径、工作区和必要输入位置，不声称 skill 会自动发现所有历史任务。

例如比较两家报价时，甲方费用核算可已完成；乙方缺书面报价的单元应阻塞，比较草稿与最终选型应分别记录。乙方资料补齐后接着比较，不能因旧记录有“已完成草稿”就宣布整个采购建议完成。
